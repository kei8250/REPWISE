# 部位からの分析選択・種目名入力・不要記録の整理

基準：ローカルの `5f17f91`。公開デプロイ・PRマージ・D1 migration・Cloudflare API操作・実ユーザー記録の変更は行っていない。

## 利用者向けの変更

- 詳細分析の種目選択のすぐ上に「部位を選ぶ」を追加。部位を選ぶと種目候補と表示中の分析を同時に切り替える。下部の部位フィルターとも連動し、期間サマリーは全身を維持する。選択部位が現在の期間にない場合は全体の候補へ戻し、上部操作が消えないようにした。
- 種目作成の名前欄を、狭い横並びのInputから、ラベル付き・全幅・3行のTextareaへ変更。日本語の長い名前を折り返して確認できる。保存する名前は改行なし、80字上限のまま。部位・作成ボタンも高さ44px以上にした。
- 設定は「不要な記録を整理」と「種目の設定」を中心にした。通常の保存件数・未同期件数・キュー・原本等は閉じた「詳細・トラブルシューティング」に移動。
- 「不要な記録を整理」を開くと入力途中の一覧からスワイプ/「…」で削除できる。古い入力不正や競合で止まる記録にも「この記録を削除」を用意。完了扱いの不要記録も対象にできる。削除の通常通知は削除結果と取り消しが中心で、細かい反映状態は展開時だけ表示。
- 設定のrep下限/上限は「目標回数の下限/上限（回）」にし、設定欄の入力高さも広げた。

## なぜ端末だけ削除され、反映が止まるのか

端末の削除と送信は分離されている。古い更新がHTTP 400等で `blocked` になると、後続のdeleteも同じ記録のFIFOの後ろで停止する。削除自体の問題とは限らず、削除前の古い入力が原因でも残り続ける。旧APIのactive削除に対する完了要求、通信失敗、認証失敗、別端末のversion競合も区別が必要。

今回、実際のIndexedDBに「入力不正でblockedになった更新」を保存してから、設定でその記録を削除する操作を再現した。従来は先頭更新で停止するが、変更後は追加の復旧操作なしで削除まで反映される。

公開サイト上のユーザー端末のキューは取得していないため、ユーザー報告個体の原因を断定していない。今回確かめたのは最新コードと旧保存形を再現したテストデータ。

## 自動処理の安全条件

`recoverPendingDeletion` は、最新の意図がdeleteで、先頭がblocked、送信中やconflictがない場合だけサーバー状態を照合する。

- サーバーが先頭更新のbaseVersionと同じなら、その更新は現在のサーバー状態を進めていない。古いキューとローカル記録を原本に残し、サーバーの有効なsnapshotで新しいdeleteだけを作る。
- サーバーが既に削除済みで、古い試行が適用される余地もなければ、原本保護後に残存キューを整合する。
- サーバーが別の端末で更新された、存在を確認できない、通信失敗、読めない形式、取り消しなどが途中で入った場合は推測で破棄しない。明示的な確認または通常の通信再試行を待つ。
- 照合から整理までにdraft/queueが変わっていないかトランザクションで比較する。古い要求を送信原本のまま書き換えず、アーカイブへ保護する。正常な別記録には触れない。
- 自動の作り直しは削除意図ごとに一度まで。`automaticDeletionRepairVersion` を端末に保持し、旧APIがdelete自体を400にし続けても、無限に別要求を生成しない。
- キュー変更後の確認は750msにまとめる。通常の文字入力は既存の入力停止待ちを尊重し、入力ごとの送信には戻さない。

自動処理の範囲外の削除を、成功したと偽って扱うことはしない。原本・tombstoneは保持し、競合がある場合だけ平易な削除確認を出す。生のHTTPエラーや内部情報は詳細画面に残す。
