# 履歴の分離・完全削除・入力修正後の自動保存

基準コミット：`63c3ec5`。本変更はローカルで実装・検証し、公開環境や実ユーザーの記録は操作していない。

## 利用者から見た動作

- 完了済みには実績のある完了記録だけを表示。編集中の古いactiveキャッシュは完了した基準データを参照し、入力途中と完了済みへ二重表示しない。
- 実績のない完了フラグや、削除済みの記録を完了一覧へ出さない。削除後は両一覧・ホーム・カレンダー・分析の表示対象から外す。
- 入力途中・完了済みのどちらからも削除可能。確認は「元に戻せません」の1回。削除の状態確認・取り消し・復元の操作はなくした。
- 日付・種目・部位の検索は必要時に開く。通常は記録一覧を先に見られる。
- 設定から同期間隔、削除反映待ち一覧、削除状態未確認の表示と確認操作を撤去した。削除した記録の名前や確認操作は詳細・トラブルシューティングにも出さない。

「削除状態が未確認」は旧データに削除完了ACKの印がない、という内部状態だった。利用者が確認するものとして表示するのをやめ、裏で削除を完了させる。

## 完全削除

新しい画面の削除は `payload.permanentDelete: true` を送る。通常の変更・完了とは異なり、**特定IDを消す終端操作**として扱う。

1. 端末ではその記録の古い更新・作成・完了・失敗キューを整理して、IDだけで処理できる削除要求を作る。送信中の古い応答が戻ってもキューから消えた要求は採用しない。他の記録には触れない。
2. サーバーは削除対象ID・owner・要求IDを検証し、削除する内容の重量・回数・目標の妥当性には依存しない。不正な古い入力で削除を止めない。
3. 完全削除は現在のserver versionを読み、トランザクション内で照合する。照合中に古い操作が先行した場合は最大3回再読込し、同じ対象の最終削除を完了する。通常の更新・完了のversion検証は維持する。
4. 未同期の作成がまだサーバーにない場合も、内容を含まない削除識別行を作る。後から届いたcreate/replaceで復活しない。
5. 実績セット・種目記録・メモ・評価・名前・元記録への関連・元の日時を消す。削除元を使った次回目標も除去し、過去の同期応答に含まれる記録内容も最小の削除情報へ置換する。
6. クライアントはサーバーの `permanentlyDeleted` 応答を確認してから、端末の原本・古いキュー・編集基準も消す。残すのは再送による復活防止に必要なID/version等の識別情報だけ。削除完了前に通信が切れた場合は表示を戻さず、自動再送する。
7. 完全削除後の旧更新・旧復元には `WORKOUT_PERMANENTLY_DELETED` (410) と削除識別情報を返す。別端末もそれを適用して古いキャッシュとキューを整理する。削除した内容は復元できない。
8. 旧版で削除済みになっていた記録も起動後に同じ完全削除へ移行する。ユーザーに状態確認を求めない。

これはworkout行を元の内容のままsoft deleteする動作ではない。個人の記録内容を消し、遅い再送・二重送信を拒否するための識別行と要求のfingerprintだけを残す。ユーザーの実データは今回の作業では削除せず、テスト用データだけで検証した。

互換性のため旧soft-delete要求の処理は残すが、新しい画面にrestore操作はなく、完全削除された対象は旧クライアントからも復元できない。クライアントとサーバーは同じリリースで更新する。旧サーバーの応答を完全削除成功と偽らない。

## 不適切な値と保存

- 任意の目標重量・目標回数に不正な値があっても、実績の保存は止めず、目標を `null`（画面上は未設定）として扱う。実績の重量・回数は変えない。
- 実績の不正値は入力欄で修正する。架空の回数や重量へ変換して成功扱いにしない。
- ユーザーが正しい内容へ修正した後は、古いHTTP 400の要求が後続の修正を塞がないようにした。最新版の入力が検証を通り、サーバーも失敗要求のbaseVersionのままの場合だけ、原本を保護して新しい修正要求に整理する。
- 別端末による実績の変更、通信・認証エラーは入力値の問題と混同しない。400を一律に成功扱いしたり、未修正の内容を無限再生成したりしない。
