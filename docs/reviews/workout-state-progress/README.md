# 完了状態・削除同期・セット別の進歩を改善

## 確認した原因と修正

| 指摘 | 原因／修正前 | 修正後 |
| --- | --- | --- |
| 完了記録の編集キャンセルで入力途中になる | 端末の完了が未同期のときも、キャンセル先にサーバーの古いactiveスナップショットを使用。completedの判別値にactiveの本体を保存していた | 編集前の完了スナップショットを端末へ保存。キャンセルはこれをトランザクションで復元し、終了時刻・評価・メモ・セットを保持。既に送信キューへ入った変更は捨てない |
| 再読み込み・別タブでも不整合が続く | 不整合のある端末キャッシュが新しい更新時刻で詳細表示に優先される | 不整合キャッシュは、最新の送信済み完了スナップショット、またはサーバーの確認済み完了データから修復。未送信編集・正常な記録を上書きしない |
| 削除→取り消し→再削除がHTTP 400 | ストアはactiveの削除・復元に対応していたが、HTTP入口のバリデーションがdelete/restoreにもcompletedを要求していた | delete/restoreはactive/completedを受け付ける。complete/editの完了状態の条件は維持。実際のHTTPハンドラーとSQLiteを通した回帰テストを追加 |
| 種目終了後に「次に取り組むSET 3」が残る | 種目の状態だけをcompletedにし、セット状態を変更していなかった | 未入力セットのスキップを確認し、有効な入力済みセットは完了、空欄は未実施にする。部分入力や不正値は修正を求める。終了後は次の未完了種目／ワークアウト終了へ案内 |
| トップ／バックオフで重量が違うと進行判定を保留 | 同重量の全セットを前提とした一括ルールだけを使用 | セットに通常・トップ・バックオフの役割を保存。重量や役割が異なる場合は、有効な完了セットごとに進行を判定。未実施セットは達成扱いにしない |
| 10〜10回に10回でも「目標下限を達成」 | 上限達成と下限達成の表示が共通 | 「目標達成・上限10回を達成」と表示。8〜12回に10回なら「目標下限を達成・上限まであと2回」 |
| 左右共通の重量の意味が曖昧 | 入力基準が保存されず、左右の回数を合算する計算だけを使用 | 種目作成・設定で重量基準を選択。各セットのスナップショットに保持し、記録と履歴に表示。履歴一覧・評価・分析のボリュームに同じ基準を使用 |
| 削除画面では同期結果が分からない | 履歴上の失敗通知は設定への案内だけ。削除詳細の再試行表示も操作できない | 履歴と削除詳細に同期中・同期待ち・同期済み・失敗理由・再試行を表示。履歴の再読み込み後も反映待ちを確認でき、同じ画面で再試行できる。取り消しの同期も区別 |

編集のACKも修正。先行する完了ACKで未送信の編集やキャンセル基準を失わず、保存した編集のACK後にはcompleted_editを残さない。画面の初期読み込み時は最新の端末データを再確認し、読み込み中に行われた編集を古い取得結果で戻さない。

## セット別の進歩

- 通常セットは従来どおりセット位置で参照。トップ／バックオフは同じ役割内の順番で参照し、並べ替えでも別の役割を混ぜない。未実施・未完了・無効な実績は参考実績にしない。
- 役割も重量基準も一致する前回の実績・セットメモ・種目メモを表示。フォームの良否は自動判定せず、メモを並べて確認する。
- 重量変更時は重量差だけでなく回数差も表示する。
- セット別判定は、そのセットの整合する保存済み回数範囲を使い、未設定・不整合なら種目設定の範囲を使う。上限達成ならそのセットに種目の増量幅を加え、未達ならその重量で上限回数を目指す。
- 例：トップ62.5kg×8回（6〜8回目標）→65kg。バックオフ60kg×10回（10〜12回目標）→60kg維持。もう1つのバックオフ60kg×12回→62.5kg。
- APIの進行状態に`set_specific`、セット別提案に`setDecisions`を追加。全セット一律の「増量／同重量／データ不足」と区別する。評価の件数表示・分析も対応。
- 自動提案は未確定。記録画面の明示操作と確認の後にだけ、同じ役割の未完了セットの目標へ採用できる。実績や完了セットは変更しない。
- 従来の同重量セットの一括進行ルールと、既に確定した次回目標は維持。

## 重量の基準と計算

| 基準 | 入力例 | ボリューム |
| --- | --- | --- |
| 片側1回で扱う重量（既存記録の既定値） | ワンハンド：ダンベル片手20kgなら20kg。ブルガリアン：両手に10kgずつ持って片脚で支えるなら20kg | 入力重量 ×（右回数＋左回数） |
| 左右の重量の合計（片側は半分） | 右20kg＋左20kgなら40kg | 入力重量 ÷ 2 ×（右回数＋左回数） |

右10回・左8回なら、どちらの入力例も360kg・回。左右別の進行判定は従来どおり少ない側の回数を使用する。最大重量・推定1RMは片側1回の負荷へ換算し、入力基準を変えただけでPRにならないようにする。目標重量と増量幅も、選択した入力基準で入力する。

設定変更は新しく追加する種目に反映。過去の入力値や重量基準を推測で変更しない。基準が違う記録との単純な重量差比較・自動提案は止めて理由を示す。標準種目の計算は維持。

## 実行方法・適用状況

専用Chromiumプロファイルをデバッグ9223番、ローカル開発サーバーを3000番で起動して実行する。ブラウザーのlocalhost:3000の保存領域を初期化するため、普段使いのプロファイルは使わない。

```sh
node scripts/review-draft-cleanup-side-reps.mjs --state-progress
```

合成データと専用IndexedDBで検証し、APIはテスト応答へ差し替える。追加の検証タブも同じテストAPIを使い、終了時には閉じる。実ユーザーの記録は変更していない。

`drizzle/0007_set_roles_and_load_basis.sql`を生成したが適用していない。追加列は種目マスターの`load_basis`、セットの`role`・`load_basis`のみ。既存値の書き換えはなく、既定値は通常の役割／片側1回の負荷。新しい列を持たない旧mutationのJSONに既定値を追加せず、既存の再送fingerprintを維持する。

FIFO、atomic claim、同一mutationの再送、version競合の保護は維持。依存パッケージの更新なし。公開デプロイ・PRマージ・D1 migration適用・Cloudflare API操作は未実施。本PRは未マージのPR #7をbaseにしている。

## 残る制約

- 実機Safari・OSのソフトウェアキーボード／日本語IMEは未確認。ブラウザーの狭い幅とタッチ操作で検証した。
- セット別の目標は確認付き採用後に保存され、保存済みメニューのコピーでも保持する。従来の一括「次回目標に設定」は単一重量用のまま維持し、セット別提案を一律重量へ変換して保存しない。
- 古い記録のトップ／バックオフや重量基準は推測で割り当てない。フォームの評価も自動推定しない。
- 通信障害・認証切れ・他端末とのversion競合を自動で解消する変更ではない。失敗時も記録とキューを保持し、同期状態と再試行を表示する。
- 公開環境への反映には、既存の未マージPRと追加列のレビュー・通常のリリース手順が必要。
